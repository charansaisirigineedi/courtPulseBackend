# CourtPulse Backend Agent Rules

This file captures the conventions future agents should follow when working in this codebase.

## Project Context

- CourtPulse is a badminton tournament management backend.
- Current stack: Java 21, Spring Boot, PostgreSQL, Spring Data JPA, Flyway, Lombok, Maven, REST APIs.
- Authentication is not implemented yet. Do not add auth flows unless explicitly requested.
- Use shared layer packages under `com.amigos.courtpulse`.
- DTOs may be grouped by feature under `dto`, for example `dto.player` and `dto.club`.

## Package Structure

Use these shared layer packages consistently:

- `config`: application configuration classes and bean definitions.
- `controller`: REST controllers.
- `dto`: request and response DTOs grouped by feature when useful.
- `dto.common`: shared API response DTOs.
- `entity`: JPA entities mapped to database tables.
- `enums`: shared enum types.
- `exception`: application exceptions and global exception handling.
- `mapper`: mapping code between entities, DTOs, and external models.
- `repository`: Spring Data repositories.
- `security`: security configuration, filters, authentication, and authorization support.
- `service`: service interfaces.
- `service.impl`: service implementations.
- `util`: small shared utilities.
- `validation`: custom validators and validation annotations.

Keep `package-info.java` files for package intent.
Do not create feature-root packages such as `com.amigos.courtpulse.club.*`; keep classes in the shared layer folders.

## Naming Rules

- Entities use singular names, for example `Player`.
- Enums must end with `Enum`, for example `PlayerStatusEnum`.
- Controllers end with `Controller`.
- Services end with `Service`.
- Service implementations end with `ServiceImpl`.
- Repositories end with `Repository`.
- DTOs should describe their API role, for example `CreatePlayerRequest`, `UpdatePlayerRequest`, `PlayerProfileResponse`.
- Flyway migrations follow `V{number}__description.sql`.

## Architecture Rules

- Controllers call services only.
- Services contain business rules and transaction boundaries.
- Services use repositories, mappers, generators, and utilities.
- Repositories access entities.
- DTOs stay at API boundaries and must not be persisted directly.
- Do not expose entities from controllers.
- Do not expose sensitive fields such as `passwordHash`.
- Prefer service interfaces with implementation classes.
- Use constructor injection only.
- Prefer Lombok `@RequiredArgsConstructor` for constructor injection.
- Do not use field injection.

## API Response Rules

- Controller methods should return `ResponseEntity<ApiResponse<T>>`.
- Use `ResponseUtil` for success and error responses.
- Use explicit HTTP status codes.
- Successful responses should include a clear message and `data`.
- Error responses should include status code, status text, message, path, and validation errors when applicable.
- Global exception handling belongs in `GlobalExceptionHandler`.

## Validation And Errors

- Use Jakarta Validation on request DTOs.
- Use custom exceptions for domain failures.
- Map duplicate resource conflicts to `409 CONFLICT`.
- Map missing resources to `404 NOT_FOUND`.
- Map validation failures and bad input to `400 BAD_REQUEST`.
- Do not let database or framework exceptions leak raw details to API clients.

## Persistence Rules

- Use Flyway for schema changes.
- Keep JPA entity mappings aligned with migrations.
- Use `LocalDateTime` for timestamp columns.
- Use `EnumType.STRING` for enums.
- Use database constraints for uniqueness where required.
- Business identifiers that must be immutable should be marked `updatable = false` in JPA.
- Use lifecycle hooks such as `@PrePersist` and `@PreUpdate` only for simple timestamp maintenance.

## Utility Rules

- Use `ObjectUtil.isNull(value)` instead of `value == null`.
- Use `ObjectUtil.nonNull(value)` instead of `value != null`.
- Use `ObjectUtil.isEqual(left, right)` or `ObjectUtil.isNotEqual(left, right)` instead of direct `.equals(...)` for object comparison.
- Use `ResponseUtil` for standard API responses.
- Keep utility classes `final` with private constructors.

## Code Generation Rules

- Generated business codes should be deterministic when possible.
- Prefer database sequences over random generation.
- Player codes are generated from `player_code_sequence` and encoded as uppercase base-36 with `CP` prefix.
- Player codes must remain length 6, uppercase, unique, immutable, and alphanumeric.

## Player Module Rules

- `playerCode` is generated by `PlayerCodeGenerator`; clients must not set it.
- `username` is required, unique, and immutable after creation.
- `email` is optional and unique when present.
- Email values are normalized to lowercase before persistence.
- `password` from requests must be hashed with BCrypt.
- Only `passwordHash` is stored.
- `passwordHash` must never be returned in API responses.
- Player updates may change only `name`, `gameName`, and `email`.
- Player search should search `name`, `gameName`, and `playerCode` case-insensitively and return at most 20 results.

## Mapper Rules

- Keep mapping explicit and simple for small mappings.
- Avoid adding MapStruct until mapping complexity justifies the dependency.
- Mappers must not expose sensitive fields.

## Security Rules

- Use stateless JWT authentication through Spring Security OAuth2 Resource Server.
- `POST /api/v1/auth/login` is public.
- `POST /api/v1/players` is public while player registration is part of the Player API.
- All other application endpoints require a bearer token unless explicitly documented otherwise.
- JWTs use HS256 and include `sub` as username plus `playerCode` as a claim.
- Protected APIs should infer the current player from the JWT. Do not require clients to send `playerCode`, `ownerPlayerCode`, or `reviewerPlayerCode` when it represents the authenticated user.
- Store the JWT secret in `JWT_SECRET`; production must not rely on the local default.
- Do not add refresh tokens until a persistence and revocation model is designed.
- Do not add roles/authorization policies until the domain rules are explicitly requested.

## Club API Sync Rules

- Mobile should use `GET /api/v1/clubs/my` as the source of truth for clubs the current player belongs to.
- Mobile should use `GET /api/v1/clubs/requests/my` as the source of truth for join request status badges.
- Club membership actions must infer the current player from JWT.
- Owners cannot leave their own club until an ownership transfer or close-club workflow exists.

## Testing And Verification

- Prefer running `./mvnw test` after changes.
- Current known issue: Maven wrapper metadata is missing at `.mvn/wrapper/maven-wrapper.properties`, so `./mvnw` cannot run until the wrapper is repaired.
- If the wrapper is repaired, use it instead of assuming system Maven exists.

## General Code Style

- Keep changes scoped to the requested module or convention.
- Favor production-ready code over demos.
- Use meaningful logging in service implementations for important lifecycle events.
- Keep comments sparse and useful.
- Avoid unrelated refactors.
